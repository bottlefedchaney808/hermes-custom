# The fleet

Three Hermes profiles live on this machine and they are three separate
installations. This directory is the single source of truth for what belongs in
each one, and `fleet` is the tool that makes the disk agree.

```
fleet.yaml          what belongs where            <- edit this
fleet/              the engine
skills/claude/      skills authored here, for Claude Code
skills/hermes/      their Hermes twins            <- GENERATED by `fleet port`
fleet.cmd           the CLI launcher
```

## Why this exists

Hermes resolves agent plugins from exactly one directory — `get_hermes_home() /
"plugins"`, in `hermes_cli/plugins_discovery.py` — with no shared path and no
search list. Skills and skins work the same way. There is no "install once for
all profiles", and there never will be.

So three profiles meant three hand-managed trees, and by the time this was
written they had already drifted in ways nothing on the machine could report:

- `claude-code` was a **live symlink** on `default` and a **frozen copy** on
  `local` and `tiferet` — three profiles running two different versions of the
  same plugin, silently.
- The 101-skin pack was on two profiles of three. `tiferet` had zero.
- `default` carried 108 skills, `tiferet` 59, with no record of why.

Every one of those is now declared, enforced, and visible.

## The model

**Declare intent in `fleet.yaml`. Let `fleet sync` materialize it.** Nothing is
installed by hand. Every path is a link back into this checkout, so `git log` is
the audit trail and a re-clone of Hermes is a one-command recovery.

### The rule that explains most confusion

| | Scope | Root |
|---|---|---|
| Agent plugins | **per profile** | `<home>/plugins/` |
| Skills | **per profile** | `<home>/skills/[<category>/]` |
| Skins | **per profile** | `<home>/skins/` |
| MCP servers | **per profile** | `<home>/config.yaml` |
| Desktop plugins | **GLOBAL** | `~/.hermes/desktop-plugins/` |

Desktop plugins are global deliberately. `apps/desktop/electron/desktop-plugins-root.ts`
actively migrates any `profiles/<name>/desktop-plugins/*` up into the app-level
root, because "profiles are agents; anything discovered through a profile's
folder appeared and disappeared with the active profile." A desktop plugin
extends the **app**, not an agent. Never install one into a profile — it will be
moved out from under you.

### Unified packages

A package holding both `plugin.yaml` and `desktop/plugin.js` gets the best of
both: the agent half installs per profile, and the desktop app copies the
desktop half out to `~/.hermes/desktop-plugins/<name>/` by itself, re-copying
whenever `plugin.js` is **newer**. `hermes-fleet` is built this way — one
manifest entry, both halves, no duplication.

Consequence worth remembering: editing `ui-src/` changes nothing until you
rebuild, because the app watches the built artifact's mtime, not the sources.

### Link, copy, or defer

The default is a directory symlink. Two things break that, and both are real
cases in this repo, not hypotheticals:

- **`mode: copy`** — for a package that writes inside its own folder. A
  symlinked package writing to itself dirties this checkout.
- **`kind: external`** — for a package whose installer assembles a payload from
  elsewhere in its own repo. `token-optimizer` is the worked example: its Hermes
  plugin imports three sibling modules that live under
  `skills/token-optimizer/scripts/`, plus a generated `measure-path` locator. A
  bare symlink of `hermes/` installs a plugin whose imports are broken — a
  regression upstream has already shipped and fixed once. Fleet reports it and
  runs nothing.

### Staging

`enable: staged` means two different things and conflating them is a trap:

- For a **plugin**, staging is honest: materialize it, leave it out of
  `plugins.enabled`, and it sits inert until one switch flips.
- For a **skill**, there is no such gate. A skill directory that exists is a
  skill that is loaded and serialized into the skills prompt on every single
  turn. "Install LifeOS's 73 skills but don't roll them in yet" cannot be
  honoured by installing them.

So a staged skill surface is **withheld** — `fleet status` shows `HELD` and says
why. Committing it means editing `fleet.yaml`, which makes the decision a diff
rather than a hidden state file.

## The tiering

| | `default` | `local` | `tiferet` |
|---|---|---|---|
| Role | daily driver | local model on GPU | **construction only, company-facing** |
| takeoff-lens | ✅ | ✅ | ✅ primary |
| core (claude-code, delegate-task-advanced, token-optimizer, brain-rag, skins, fleet) | ✅ | ✅ | ✅ |
| the lab (dynamic-workflows, self-evolution, bot-kit) | ✅ | ✅ | ❌ |
| desktop plugins | — global, once — | | |

`tiferet` stays narrow on purpose. It is the profile customers talk to, and
every skill added to it is context paid for on every turn. It still does
takeoffs — that is most of what it does — it just doesn't get the lab.

## Commands

```bash
fleet status              # what is installed where, and what drifted
fleet status -v           # every surface
fleet status -v -a        # ...including the ones already in sync

fleet sync                # DRY RUN
fleet sync --apply        # make the disk match fleet.yaml
fleet sync --apply -p tiferet     # one profile
fleet sync --apply -k takeoff-lens  # one package

fleet enable  <package>   # add its plugin ids to plugins.enabled, per profile
fleet disable <package>
fleet port                # regenerate skills/hermes/ from skills/claude/
fleet docs                # regenerate every package's HERMES.md
fleet json                # the whole state, machine-readable (what the UI reads)
```

Every command dry-runs by default. Nothing writes without `--apply`.
`enable`/`disable` back up each `config.yaml` before touching it and edit only
the `plugins.enabled` list as text, so the comments and ordering in an 18 KB
hand-tuned config survive byte-for-byte.

After any enable or disable: `hermes gateway restart`.

### Verdicts

| | meaning |
|---|---|
| `ok` | disk matches the manifest |
| `NEW` | declared, not installed yet |
| `LINK` | a link pointing somewhere else |
| `CONV` | a real copy where the manifest wants a link — the drift case |
| `SYNC` | mirror contents differ (skins) |
| `HELD` | staged, deliberately withheld |
| `MISS` | owns its own installer and hasn't been run |
| `man` | needs a human (MCP registration, a deploy script) |

## Adding something

1. Put the source in this checkout.
2. Add a `packages:` entry — surfaces, profiles, and a `notes:` explaining *why
   those profiles*. That note is the one piece of prose that survives; the rest
   of the docs are generated from it.
3. `fleet sync` → read the plan → `fleet sync --apply`.
4. `fleet enable <name> --apply` if it needs allow-listing.
5. `fleet docs --apply` and commit.

## The UI

`hermes-fleet` renders all of this as a pane in Hermes Desktop and a tab in the
web dashboard, from one backend, on an open widget grid other plugins can
register into. See [hermes-fleet/HERMES.md](hermes-fleet/HERMES.md).

## Guarantees, and their limits

- **Idempotent.** Running `fleet sync --apply` twice must produce a clean no-op
  the second time. If it doesn't, that's a bug here, not a quirk to route around.
- **Dry run by default**, everywhere.
- **The manifest is the allowlist.** No command — CLI or HTTP — takes an
  arbitrary path, a shell command, or a package `fleet.yaml` doesn't declare.
- **Backups before every config write**, with a collision-safe name.
- It does **not** manage upstream-installed plugins (`hermes plugins install`).
  Those are reported, never touched; `.install-metadata.json` records their
  provenance and fleet reads it.
- It does **not** register MCP servers. That is a structured edit to a live
  config for something that launches a process, and it stays a human's call.
