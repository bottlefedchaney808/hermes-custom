# Porting skills between Claude Code and Hermes

## The thing everyone gets wrong first

**The file format is already identical.** Not similar — identical.
`~/.claude/skills/brainstorming/SKILL.md` and
`~/.hermes/profiles/local/skills/brainstorming/SKILL.md` are byte-for-byte the
same file on this machine right now: the same `SKILL.md`, the same
`name` / `description` YAML frontmatter, the same body.

So porting is **never** a format conversion, and any tool that claims to
"convert" a skill is doing nothing. What actually differs is two things:

1. **Tool names.** A skill that says "use the Read tool" is naming a tool that
   does not exist in Hermes. That instruction doesn't degrade — it misfires.
2. **Paths.** `~/.claude` is one directory. Hermes has four homes (the default
   plus three profiles) and which one is live depends on the active profile, so
   a hard-coded path is a bug waiting for a profile switch.

A distant third: Hermes namespaces skills one directory deep
(`skills/<category>/<name>/SKILL.md`) where Claude Code is flat. Both shapes are
valid in Hermes; the category is for your own organization.

## Layout

```
skills/
  claude/           SOURCE OF TRUTH. Edit here.  -> installs to ~/.claude/skills
  hermes/           GENERATED by `fleet port`.    -> installs per profile
  PORTING.md        this file
```

Never hand-edit anything under `skills/hermes/`. Each generated `SKILL.md`
carries a header saying where it came from and how to re-port, and the next
`fleet port --apply` overwrites it.

```bash
fleet port                 # dry run — lists every substitution it would make
fleet port -v              # ...and shows each one
fleet port --apply         # regenerate skills/hermes/
fleet port hermes-fleet --apply    # just one
```

## The tool map

Verified against the Hermes checkout (`tools/file_tools.py`,
`tools/web_tools.py`, `tools/terminal_tool.py`, `tools/todo_tool.py`) — not
guessed. If you add a row, verify it the same way.

| Claude Code | Hermes | Toolset |
|---|---|---|
| `Read` | `read_file` | `file` |
| `Write` | `write_file` | `file` |
| `Edit` / `MultiEdit` | `patch` | `file` |
| `Glob` / `Grep` | `search_files` | `file` |
| `Bash` / `BashOutput` / `KillShell` | `terminal` | `terminal` |
| `WebFetch` | `web_extract` | `web` |
| `WebSearch` | `web_search` | `web` |
| `Task` / the Agent tool | `delegate_task` | `delegation` |
| `TodoWrite` | `todo_list` | `todo` |
| `AskUserQuestion` | `clarify` | `clarify` |
| `NotebookEdit` | `patch` | `file` |

Hermes toolsets a skill may reference: `file`, `terminal`, `web`, `delegation`,
`todo`, `clarify`, `skills`, `memory`, `browser`, `vision`, `computer_use`,
`code_execution`, `session_search`, `cronjob`, `kanban`, `a2a`, `connections`,
`context_engine`, `image_gen`, `tts`, `x_search`.

## The path map

Longest prefix first — otherwise the bare `~/.claude` rule eats the specific
ones.

| Claude Code | Hermes |
|---|---|
| `~/.claude/skills` | `$HERMES_HOME/skills` |
| `~/.claude/plugins` | `$HERMES_HOME/plugins` |
| `~/.claude/agents`, `~/.claude/commands` | `$HERMES_HOME/plugins` |
| `.claude/settings.json` | `$HERMES_HOME/config.yaml` |
| `~/.claude` | `$HERMES_HOME` |
| `CLAUDE.md` | `AGENTS.md` |
| `claude -p "…"` | `hermes chat -q "…"` |

`$HERMES_HOME` is deliberate. Writing `~/.hermes` in a ported skill is wrong
whenever a named profile is active, and it will be wrong silently.

## What the port refuses to do

Some Claude Code concepts have no Hermes equivalent, and inventing one would be
worse than leaving the gap visible. These are **flagged, not translated**:

- `ExitPlanMode` / `EnterPlanMode` / plan mode
- the `SlashCommand` tool
- `.claude-plugin/`, `marketplace.json`, `hooks.json`
- `CLAUDE.local.md`

`fleet port` prints a warning naming each one and the file it is in. Fix those
by hand in the Hermes twin — or better, rewrite the Claude-side skill so the
instruction is expressed in terms both hosts have, and re-port.

## Adding a skill to the split

1. Write it under `skills/claude/<name>/`. Write it for Claude Code; that is the
   source.
2. `fleet port --apply`.
3. Read the warnings. If the port flagged something, decide what the Hermes
   version should say and fix the *Claude* side if you can.
4. Add it to `fleet.yaml` — a `claude-skill` surface for the Claude half, a
   `skill` surface (with a `category`) for the Hermes half, and the profiles it
   belongs to.
5. `fleet sync --apply`.

## Skills that do not need this

A skill that already ships both halves upstream is not ported — it is installed
twice from its own sources. `token-optimizer` is the example: it ships
`.claude-plugin/` and `hermes/`, both maintained by its author. Re-porting it
here would fork it. `fleet.yaml` installs each half from upstream and stays out
of the way.
